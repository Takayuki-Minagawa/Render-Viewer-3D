# UI更新の比較（2026-09-07）

対象は基準commit `eb75164fe1d6e71311d7913810d509e13e319b79` の旧 MaterialLibraryView と今回の実装。Node.js 22.18.0 / linkedom、同一プロセス・同一端末、100材質・200割当の固定データで、初期描画後に10回warm-up、60回計測した。カメラ変更時を模擬して、材質・割当は不変の参照を渡した。現在のStoreは変更のない領域を構造共有し、AppShellも割当配列を再利用する。

| 材質ライブラリ更新 | 中央値 | p95 | 一覧replaceChildren呼出数（warm-up込み70回） |
| --- | ---: | ---: | ---: |
| 変更前 | 1.601 ms | 5.401 ms | 70 |
| 変更後 | 0.000083 ms | 0.000084 ms | 0 |

変更後は不変の入力に対する早期returnであるため、微小な時間値は実用上のブラウザ処理速度を表すものではない。ここで確認した改善は、カメラ更新で不要な材質DOM処理を実行しないことである。ブラウザの入力から描画までの遅延・GPU負荷・実機p95は別途検証する。

実装は一覧行を材質IDで再利用し、変更行の内容だけを更新する。材質使用数を1回の走査で索引化し、カテゴリ／プリセット候補も内容・言語が変わった場合に更新する。`tests/ui-reconciliation.test.mjs` は行・子DOMの同一性、変更行の更新、削除、選択状態、入力transactionを検証する。
